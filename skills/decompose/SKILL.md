# План

План — до изменений: сбор контекста, уточнение, подходы, карта файлов. Вход — номер задачи: `/decompose <N>`.

- **Только с номером** — без номера, до любого чтения, выведи «Плана без задачи нет: заведи задачу (груминг, шаг 4) и вызови `/decompose <N>`» и остановись.
- **До утверждения ничего не меняешь** — ни файлы проекта, ни задачи на GitHub; исключения — свой план `plans/<slug>.md` и файлы во временной папке сессии. Заведение подзадач и закрытие задачи (эпик, отказ) — после подтверждения пользователя. После утверждения — по разделу «После утверждения».
- **Задача #N** — задача на GitHub, всегда с номером; **задача плана** (в шаблоне «Задача K») — пункт плана.

## Этап 1. Разбор намерений и сбор контекста

Старт — задача #N одной командой `gh issue view <N> --json title,body,comments --jq '.title, .body, (.comments[].body)'` и журнал `plans/journal/groom-<N>.md` («Контекст груминга»); журнала нет (груминга не было) — контекст с нуля.

Определи вид сам — по запросу и контексту груминга; не можешь выбрать — спроси с вариантами.

Контекст — Read, Glob, Grep до ~10 обращений, кусками (`grep -n` → диапазон строк). Сверх бюджета — одной строкой «читаю сверх бюджета: что и зачем» и читай; на ≈ 20 обращениях — остановись: «нужно больше контекста: <что и зачем>» и вопрос пользователю.
- фича — точка входа, похожее решение (паттерн), что от неё зависит;
- баг — причина с источником `файл:строка`: файлы из описания, `git log` по файлам, `git log -S <строка>`;
  воспроизвести (вне бюджета): одна команда или тест без подготовки окружения; иначе — исход «исследование»;
- рефакторинг/миграция — все места использования (кто вызывает) и тесты, которые их покрывают; тестов нет — в «Неизвестно»;
- исследование — вопрос, на который нужен ответ; что известно из документации; где ставить опыт без риска.

С контекстом груминга — добирай только недостающее. Проект и стек — из файла проекта, в резюме — только особенное.

```
Резюме:
1. Запрос: [вид] — [одна фраза]
2. Решения груминга: [#N, раздел]; подход — [название], отклонённые — [название] (без груминга — «нет»)
3. Затронуто: `путь` — что в нём
4. Соглашения проекта, которых это касается
5. Неизвестно: что выяснить до плана
```
Остановись: «правильно понял запрос?». Подтверждение резюме подтверждает и подход груминга; «пересмотреть подход» — этап 3. Дальше — после подтверждения.

## Этап 2. Уточнение

Резюме не повторяй. Четыре вопроса — одним окном инструмента (исключение из «Как спрашивать»), всегда, и с контекстом груминга: ответ из груминга — первый вариант «(рекомендую)»; ответ пользователя перекрывает любой вариант. Ответ требует уточнения — следующим окном, только по этому вопросу.
1. **Цель** — форма + что будет сделано + как поймём, что достигли. Форм четыре:
   - **одна задача** — план по шаблону;
   - **исследование** — план опыта: что смотрим, какой опыт, срок, какой ответ нужен; большой опыт — отдельной задачей-исследованием;
   - **эпик** — плана нет: подзадачи «название — проблема», порядок, вопрос «заводим в Backlog?»; сигнал — больше ~7–10 решений или план не сходится за сессию;
   - **отказ** — плана нет: причина — в «Отклонено» задачи #N; закрыть как «not planned» — решает пользователь.
2. **Объём** — наборы `путь` — зачем, «≈ N файлов → PR». PR — не больше 10 файлов, считая тесты, их данные и порождённые; больше — разбивка на блоки PR внутри плана: «PR 1: <что даёт> — ≈ N файлов». Один блок — обычная ветка; больше одного — long-ветка. Эпик — не из размера, а из смысла: разные задачи одной темы. Названный пользователем файл — обязателен.
3. **Ограничения** — найденные, с источником; нет — «ограничений не нашёл — есть?». Жёсткие (не трогать файл, только язык X) — отдельным списком; расходятся со стеком проекта — побеждает план, с пометкой. Открытое — кто решает, до какого шага.
4. **Название и slug** — 2–3 варианта «<название по-русски> — `<english-slug>`», рекомендуемый — первым, с причиной. Название — результат по-русски, без номера, типа и префикса. Slug — английский, короткий, по правилам веток: из него имя файла `plans/<slug>.md` и ветки `task/<N>-<slug>`. Вариант пользователя побеждает.

```
Контекст плана:
- Название: …
- Slug: …
- Цель: [форма] … — критерий: …
- Объём: `путь` — зачем; ≈ N файлов → PR
- Ограничения: … (нет — «нет»); жёсткие: …
- Открыто: … — кто решает
```

Эпик или отказ — этапы 3–5 не нужны: подзадачи заводятся, задача #N закрывается — только после подтверждения пользователя.

## Этап 3. Подходы

Подход выбран на груминге и резюме подтверждено — этап пропускается, в плане: «Подходы: из груминга — <название>». «Пересмотреть подход» или подхода нет — 2–3 подхода по шаблону, выбор — текстом, «Что выбираешь?», без окна:

```
Выбираем: [что решаем — одной фразой, на примере из проекта].

**Вариант А: [название]** (рекомендую — [почему, с источником])
- как работает: [на конкретном примере из проекта]
- плюсы: ...
- минусы: ...
- объём: [≈ N файлов / PR]

**Вариант Б: [название]**
- как работает: ...
- плюсы: ...
- минусы: ...
- объём: ...

Что выбираешь?
```
- 2 или 3 варианта — без придуманного для счёта; вариант один — скажи, почему других нет.
- После выбора: «Запасной: [вариант] — переходим, если [условие]»; остальные — в «Отклонено» с причиной из их минусов.
- Подход меняет объём этапа 2 — принцип «Возврат к согласованному».
- Пропуск без груминга — выбор очевиден, пользователь сказал или баг с найденной причиной; в плане: «Подходы: пропущено — <почему>».

## Этап 4. Создание плана

Файл `plans/<slug>.md` по шаблону плана; в git — после утверждения (этап 5). Только подтверждённое на этапах 1–3, новых вопросов нет.

План этой задачи уже есть — ветка `task/<N>-<slug>` или `long/<N>-<slug>` в `origin`: `git ls-remote --heads origin 'task/<N>-*' 'long/<N>-*'`, кроме `*-pr<k>` и `*-final` — это ветки выполнения. Назови ветку и путь (без пересказа) и спроси: «дополнить» / «заменить». Заменить — тот же slug: `task plan` с ним делает «Обновить план», другой slug дал бы вторую ветку плана. Молча не перезаписывай.
План сохранён `task plan` — локальной копии нет: перед правкой достань его из ветки — `git show origin/<ветка>:plans/<slug>.md > plans/<slug>.md`; сохраняй снова `task plan` (коммит «Обновить план»).

**Карта файлов** — до задач плана: что создаётся или меняется и за что отвечает. Выходит за объём этапа 2 — принцип «Возврат к согласованному».
<!-- >>> plan:decomposition -->
- Один файл — одна ответственность: описывается одной фразой без «и», иначе дели. Новый интерфейс — его вход строкой.
- Маленькие файлы; не склеивай ради лимита PR — больше PR.
- Меняются вместе — лежат вместе: группы по ответственности, не по слоям.
- Существующие паттерны; отклонение — в плане с причиной. Ничего не переделывай молча — улучшение отдельной задачей с согласия.
- Тесты — в группе под проверяемым файлом.
- Блоки PR — из групп карты: блок — законченная смысловая часть с одной целью; «что даёт этот PR» — одной фразой без «и». Меняются вместе — в одном блоке. Не по слоям (модели — PR 1, интерфейс — PR 2) и не по счёту файлов посреди смысла: не влезает в лимит — дели цель, а не список файлов.
<!-- <<< plan:decomposition -->

```
Отвечает за тело PR:
- `task/github/PrBody.kt:23` — изменить — убирает подсказки шаблона; вход: `withoutComments(text): String`
- `task/github/PrBodySpec.kt`, `PrBodySpecData.kt` — изменить — случаи комментариев
```
Известно место — `путь:строка`; новый файл или меняется целиком — путь без строки.

## Гранулярность задач

<!-- >>> plan:granularity -->
Шаги задачи:
1. Напиши падающий тест.
2. Запусти — убедись, что падает.
3. Реализуй минимальный код, чтобы тест прошёл.
4. Запусти тесты — убедись, что проходят.
5. Закоммить — тест и код в одном коммите.

- Задача = одна логическая единица (функция, эндпоинт, компонент); ~5 чекбоксов, больше — если логически атомарно.
- Тесты не откладываются в отдельную задачу.
- Рефакторинг — тот же цикл: тест под новую сигнатуру с прежними проверками → падает → код → зелёный.
- Без логики (текст скилла, шаблон, `labels.yml`) — «тест: не применим — <почему>»; есть проверка формата — она и есть тест.
<!-- <<< plan:granularity -->

## Никаких заглушек

<!-- >>> plan:no-stubs -->
Каждый шаг содержит фактическое поведение, нужное разработчику. Никогда — ни в плане, ни в коде:
- `TODO`, «not yet implemented», пустые методы;
- шаги «что сделать» без «как» — для шагов с кодом код пишется в плане; расплывчатое («добавь обработку ошибок», «добавь валидацию») — тоже заглушка: каких, что делать с каждой;
- ссылки на типы, функции и методы, не определённые ни в одной задаче и не существующие в проекте (существующие — `путь:строка`).

Шаг 2 «запуск — падает» — с ожидаемой причиной: «падает: Unresolved reference `withoutComments`»; упал по другой причине — разобраться до кода.
<!-- <<< plan:no-stubs -->

## Самопроверка

После написания плана — прогони чеклист сам, не агентом:
1. **Покрытие спецификации:**

<!-- >>> plan:coverage -->
Спецификация — критерии цели из «Обзора», «Решение» и «Критерии готовности» задачи, проектные решения из контекста груминга, жёсткие ограничения. Каждое требование → задача, которая его реализует (строкой «требование → задача N»); пробелы — списком. Обратно: задача не ведёт ни к одному требованию — вопрос «задача N не покрывает ни одного требования — убрать?».
<!-- <<< plan:coverage -->
2. **Поиск заглушек** — тревожные сигналы и всё из «Никаких заглушек».
3. **Согласованность типов:**

<!-- >>> plan:types -->
Типы, сигнатуры и имена в поздних задачах совпадают с определёнными в ранних (`foo()` в задаче 5 и `foo1()` в задаче 7 — баг); с существующим кодом — сверка по файлу (`grep -n`), не по памяти; с картой файлов — каждый файл карты есть в задаче и наоборот, входы интерфейсов совпадают с кодом задач.
<!-- <<< plan:types -->
4. **Ограничения и объём** — ни одна задача плана не трогает файл из «не трогать»; файлы задач — в объёме этапа 2 (вышли — принцип «Возврат к согласованному»); каждый блок PR — в лимите этапа 2; блок завершён сам по себе: после его PR проект собирается и тесты зелёные.

Нашёл пробел — исправь, не молча; требование без задачи — добавь задачу, не молча.

Итог — строкой: «Самопроверка: покрытие 7/7, заглушек 0, типы — исправлено 1 (`foo1` → `foo` в задаче 7), ограничения — ок».

## Этап 5. Ревью и утверждение

Сообщи:
```
План готов: `plans/<slug>.md`
Самопроверка: покрытие 7/7, заглушек 0, типы — ок, ограничения — ок.
```
Вопрос инструментом (принцип 2 груминга — понятен сам по себе): «План „<название>“ готов. Что дальше?»
- **Ревью плана агентом** — свежий агент без нашего разговора проверит план: пробелы против требований, заглушки, расхождения типов, неясные шаги; замечания — пользователю.
- **Утвердить план** — план принят как есть и переходит к следующему шагу.

Ревью — агентом, не собой: самопроверка уже прошла, повторная тем же контекстом найдёт то же. Утверждает только пользователь.

### Агент ревью

Запусти одного агента `plan-reviewer` — только по имени, никогда форком: форк наследует разговор. Историю сессии не передавай — агент самостоятелен и сфокусирован на плане, без твоего хода мыслей. Контекст ревью:
- путь к плану;
- требования текстом: «Проблема», «Решение» и «Критерии готовности» задачи #N, «Контекст груминга» (итог, не история) — у агента нет `Bash`, задачу на GitHub он не прочитает.

Что проверить и формат ответа — в самом агенте (`agents/plan-reviewer.md`), здесь не повторяются.

Замечания — пользователю, сам по ним не правь: агент не видел разговора и может ошибаться. Затем вопрос снова, без ревью:
- **Утвердить план**;
- **Поправить по замечаниям** — пользователь называет, какие принять; правь не молча и спроси снова (без ревью).

### После утверждения

Сохрани план командой `task plan <N> <slug> --issue-parts <файл>` (блоков больше одного — `--long`): ветка `task/<N>-<slug>` или `long/<N>-<slug>` в `origin` без смены статуса и без PR; в тело задачи — строка «План: …» и части плана между метками `<!-- план -->`; локальный план после сохранения команда удаляет. Повтор — «Обновить план».
Файл частей готовишь ты — вне `plans/` (временная папка сессии): `plans/*.md` команды `task commit` и архив плана принимают за план. Заголовки = названия разделов задачи (`## Объём изменений`, `## Автоматически`, `## Вручную`, `## Отклонено`, …), под ними строки по таблице:

| Блок плана                             | → Раздел задачи                                                           |
|----------------------------------------|---------------------------------------------------------------------------|
| «Структура файлов»                     | «Объём изменений» — `путь` — зачем, «≈ N файлов → PR»                     |
| «Критерии цели» из «Обзора», «Приёмка» | «Критерии готовности» — командой → «Автоматически», остальное → «Вручную» |
| «После завершения»                     | «Критерии готовности» → «Вручную»                                         |
| «Обзор решения»: отклонённые           | «Отклонено» — с причиной                                                  |
| «Обзор решения»: запасной              | «Решение» — «Запасной: … — переходим, если …»                             |
| «Ограничения»: жёсткие                 | «Не входит в задачу» — «не трогаем `путь` — почему»                       |
| «Открыто»                              | «Открытые вопросы»                                                        |

- Тело задачи — для человека: что, зачем, как поймём, что готово; план — для исполнителя: задачи, код, контекст, технические детали в задачу не копируются.
- Решения груминга в задаче уже есть — план их дополняет, не переписывает; разошёлся с грумингом — строка с пометкой «изменено при плане».
- Изменения при выполнении — не из плана, а через PR в «Решено в работе».

Своих команд git и `gh` не собирай. Ветка живёт, пока не вернёмся к задаче.

Вопрос инструментом: «Как выполняем план „<название>“?»
- **Скиллом execute** — задачи по очереди выполняют агенты-исполнители, они же правят план; для многошаговой работы.
- **В этой сессии** — задачи по очереди здесь, без субагентов; для тривиального плана из одного блока, где `execute` дороже, чем сделать. Блоков больше одного — только `execute`.

- Скиллом — в новой сессии: выведи «Продолжи в новой сессии из папки проекта: `/execute <N> <slug>`». Сам `execute` здесь не вызывай: каждый его ход перечитывал бы груминг и план. Ветку берёт `execute`.
- В этой сессии — сначала ветка задачи: `task start N slug` (задача — в Groomed; задачи нет — <задача: хранение решений груминга>). Затем задачи плана последовательно, по тем же правилам: гранулярность, пять шагов, «Прогресс» (➕ ⚠️), не молча. План обновляешь сам; коммиты задач — `task commit --message-file <файл>`. PR — `task pr`: он сам перенесёт план в `plans/done/` и уберёт его из ветки.

## Как спрашивать

- **Один вопрос за раз, пример сначала.** Исключение — этап 2: четыре вопроса одним окном.
- **Выбор из вариантов** — окно инструмента для короткого самодостаточного выбора; вопрос в окне понятен сам по себе: названо, о чём речь, у каждого варианта — короткое описание. Подходы — текстом (этап 3).

## Принципы

1. **Минимальный объём** — у каждой строки объёма причина: «без неё задача не решена»; задача плана без требования — вопрос «убрать?».
2. **Не соглашайся по умолчанию** — на предложение пользователя: где оно может не сработать, чем хуже других вариантов, какие крайние случаи упускает. Своё предложение — с причиной, не пересказ примера пользователя. Решает пользователь.
3. **Возврат к согласованному** — явным вопросом «это меняет согласованное <что: объём этапа 2, решение груминга N>, меняем?».
4. **Дублирование или абстракция** — код повторяется: спроси, дублирование (проще, нет связанности) или абстракция (DRY, но сложнее); компромиссы — до решения.
5. **Факт — с источником** — точные пути `путь:строка`, если возможно; утверждение о коде — с источником (файл, опыт, вывод команды); без источника — «предполагаю».
6. **Код и команды в шагах** — полный код в каждом шаге, который меняет код; повторяющийся — допустимо «как в задаче N». Команды — точные, с ожидаемым выводом одной-двумя ключевыми строками: `./gradlew :scripts:test --tests '*PrBodySpec*'` → `BUILD SUCCESSFUL`; падение — `Unresolved reference: withoutComments`.
7. **Чужие планы не читай** — ни других задач, ни `plans/done/`; образец — только шаблон.
