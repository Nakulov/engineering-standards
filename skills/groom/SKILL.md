# Груминг

Груминг заканчивается проектными решениями. Как делать (эпик, исследование, отказ, разбивка) — решает план.

- **Ничего не меняешь** — ни файлы проекта (код, скиллы, черновики, конфиги), ни тела других задач; исключения — свой журнал `plans/journal/groom-<N>.md` и статус своей задачи командой `task groomed` (шаг 4). Запись решений своей задачи — по процессу хранения решений. Решение касается соседней задачи или скилла — не правь, собери «касается #N: <что>» для шага 4.
- **Один вопрос за раз, пример сначала.**

## Процесс

1. **Понимание идеи.**
   - Старт: задача — одной командой `gh issue view <N> --json title,body,comments --jq '.title, .body, (.comments[].body)'`. Есть `plans/journal/groom-<N>.md` — прочитай, покажи согласованное и открытое, спроси: продолжаем с открытого или заново?
   - Контекст — файлы, документация, последние коммиты по теме: до ~10 обращений, кусками (`grep -n` → диапазон строк). Не хватило — одной строкой «читаю сверх бюджета: что и зачем» и читай.
   - Задача есть — соседей бери из её тела (#N в «Не входит», «касается», блокеры), читай, когда разговор до них доходит. Задачи нет — поищи дубль и отклонённое: `gh issue list --state all --search "<слова>"`; к отклонённому не возвращайся без новой причины.
   - «Границы» ROADMAP, если он есть, — тема за границами обсуждается отдельно.
   - Фокус вопросов: назначение, ограничения, критерии успеха, точки интеграции.
   - Пунктов несколько — предложи список и порядок один раз; после подтверждения пункта сразу бери следующий: «Записал k/N: <что>. Пункт k+1/N — …». Тему вне списка сам не открывай: «всплыло: X — в список или в Backlog?».
2. **Исследование подходов.** Когда идея понятна — подходы по шаблону «Подходы».
3. **Дизайн по секциям.** После выбора подхода — секции: архитектура, компоненты, поток данных, обработка ошибок, тестирование.
   - Секция — не больше 300 слов; подтверждение после каждой, не всю разбивку сразу.
   - Неприменимая — явно: «не применима: <почему>» (пример: «Поток данных — не применима: шаблон только читается»).
   - Что-то не складывается — откатись назад.
4. **Следующий шаг** — выбирает пользователь:
   - **план** — в новой сессии: выведи «Продолжи в новой сессии из папки проекта: `/decompose <N>`». Скилл плана здесь не вызывай: план в этой сессии перечитывал бы весь груминг на каждом ходу;
   - **сразу в работу** — в этой сессии, без плана и `execute`: ветка — `task start <N> <slug>`, коммит — `task commit --message-file <файл>` (заголовок и «Файлы:» строками «- `путь` — что изменено»), PR — `task pr`.

   Правка настолько проста, что план, агенты-исполнители и ревью обойдутся дороже её самой, — скажи об этом и предложи «сразу в работу» с причиной. Пример: опечатка «опесание» → «описание» в одной строке. Решает пользователь.

   Пользователь выбрал «план» или «сразу в работу» — только тогда вызови `task groomed <N>` и покажи его ответ до «Продолжи в новой сессии…» или до работы: задача переходит из Backlog в Groomed, иначе `task start` откажет. Тема без задачи — не вызывай. Отказ (закрыта, эпик) — покажи ответ и продолжай шаг 4.

   Выведи списки «завести в Backlog: …» и «касается #N: …»; спроси, заводить ли темы (перед заведением — поиск дубля, как в шаге 1) и куда записать «касается». Итог — в журнал по шаблону «Журнал», при любом выборе.

## Как спрашивать и записывать

- Окно инструмента с вариантами — для короткого самодостаточного выбора: порядок, да/нет, варианты с описанием в строку. Вопрос в окне понятен сам по себе: названо, о чём речь (окно может не показывать текст выше).
- Подходы и секции дизайна — обычным текстом, в конце «Что выбираешь?» / «Подтверждаешь секцию?»; в окне их не пересказывай.
- Журнал — только подтверждённое, тем же ответом, что и следующий вопрос; без промежуточных пометок.
- Всплывшие темы — сразу в журнал списком «завести в Backlog: …»: при сжатии контекста не потеряются; внутри задачи их не грумь.
- Инструмент задач — если есть, веди в нём шаги и секции дополнительно; его может не быть.

## Принципы

1. **Минимальный объём** — у каждой строки объёма причина: «без неё задача не решена». Полезное, но не обязательное — в существующую задачу (#N) или «завести в Backlog», не в эту.
2. **Не соглашайся по умолчанию** — на предложение пользователя: где оно может не сработать, чем хуже других вариантов, какие крайние случаи упускает. Своё предложение — с причиной, не пересказ примера пользователя. Решает пользователь.
3. **Возврат к согласованному** — явным вопросом «это меняет согласованное решение N, меняем?».
4. **Дублирование или абстракция** — код повторяется: спроси, дублирование (проще, нет связанности) или абстракция (DRY, но сложнее); компромиссы — до решения.
5. **Факт — с источником** — `файл:строка`, опыт, вывод команды; перед объяснением решения — перечитай задачу и процитируй; без источника — «предполагаю».

## Шаблоны

### Подходы

```
Выбираем: [что решаем — одной фразой, на примере из проекта].

**Вариант А: [название]** (рекомендую — [почему, с источником])
- как работает: [на конкретном примере из проекта]
- плюсы: ...
- минусы: ...
- объём: [≈ N файлов / PR]

**Вариант Б: [название]**
- как работает: ...
- плюсы: ...
- минусы: ...
- объём: ...

Что выбираешь?
```
- 2 или 3 варианта — без придуманного для счёта; вариант один — скажи, почему других нет.
- Невыбранные — в «Отклонено» с причиной из их минусов.

### Журнал

`plans/journal/groom-<N>.md` (задачи нет — `groom-<тема>.md`; папка вне git):
```
Контекст груминга:
- Задача: [#N или тема] — [одна фраза]
- Найденные файлы: `путь` — зачем
- Выбранный подход: [название] — почему; отклонённые: [название] — почему
- Проектные решения: [по секциям дизайна, по пункту]
- Открыто: [что не решено и кто решает]

Всплывшие темы:
- завести в Backlog: …

Касается других задач:
- касается #N: …
```
