# Кодстайл JSON

Правила JSON для всех наших проектов: оформление, схемы, проверка. Читают:
- человек — когда пишет или правит JSON и проводит ревью;
- агент, который пишет JSON, — перед правкой файлов из охвата;
- агенты ревью — когда проверяют дифф с такими файлами.

## Охват

Правила действуют для JSON, формат которого задаём мы:
- схемы — `*.schema.json`;
- файлы данных и настроек, у которых есть схема;
- файлы данных, формат которых описан иначе, — например, другим файлом проекта, по которому их сверяет код.

Не входят:

| Что | Пример | Почему |
|-----|--------|--------|
| формат задаёт чужой инструмент | `package.json`, `tsconfig.json`, `manifest.json` | схему даёт инструмент, IDE берёт её из SchemaStore; `tsconfig.json` — не чистый JSON, в нём есть комментарии |
| файл пишет программа | `package-lock.json` | руками его не правят. Генератор свой — правила относятся к его выводу |
| тестовые данные, сломанные нарочно | файл с ошибкой для теста проверки | схема на нём и должна падать |

Перевод строки в конце и отступ 2 для любого `*.json` уже задаёт `.editorconfig` стандарта.

Формат данных — ключи, значения, их смысл — решает проект. Стандарт задаёт только общее для любого проекта.

## Формат правила

Тот же, что у кодстайла Kotlin, — [docs/code-style/kotlin/README.md](../kotlin/README.md#формат-правила): ID `JSON-<РАЗДЕЛ>-<N>`, «Почему», «Проверка», примеры «Запрещено» и «Разрешено» в одном блоке. «Проверка» — `проверка JSON` (команда проекта по JSON-CHECK-1) или `ревью`.

Замечание ревью ссылается на ID: «нарушено JSON-FMT-3».
