# Кодстайл Kotlin

Правила кода на Kotlin для всех наших проектов. Читают:
- человек — когда пишет код и проводит ревью;
- агент, который пишет код, — перед правкой файлов `*.kt` и `*.kts`;
- агенты ревью — когда проверяют код и имена в плане.

## Файлы

| Префикс ID | Файл | О чём |
|------------|------|-------|
| `KT-NAME` | [naming.md](naming.md) | имена модулей, пакетов, файлов, классов, функций, свойств, лямбд |
| `KT-CLASS` | [classes.md](classes.md) | классы, объекты, интерфейсы, константы, data-классы |
| `KT-FUN` | [functions.md](functions.md) | функции: расширения, ссылки, вложенные функции, аргументы вызова |
| `KT-FMT` | [formatting.md](formatting.md) | форматирование, scope-функции, управляющие конструкции |
| `KT-DOC` | [docs.md](docs.md) | импорты, псевдонимы, комментарии, KDoc, заглушки |

Отступы, длина строки и настройки IDE — в `.editorconfig` в корне репозитория.

## Формат правила

````
### KT-FUN-3. Вложенные функции запрещены
Почему: вложенную функцию нельзя протестировать отдельно, и она прячет вторую ответственность внешней.
Проверка: ревью
Источник: #16

```kotlin
// Запрещено
fun foo() {
    fun bar() {}
    bar()
}

// Разрешено
fun foo() {
    bar()
}

private fun bar() {
    // …
}
```
````

- **ID** — `KT-<РАЗДЕЛ>-<N>`, нумерация сквозная внутри раздела. Номер удалённого правила не переиспользуется: старые ссылки в замечаниях ревью и задачах не должны указывать на другое правило.
- **Почему** — причина правила. Правило без причины не добавляется.
- **Проверка** — чем ловится нарушение: `detekt <Правило>` или `ревью`. «Своё правило» — правило detekt, которого нет в стандартном наборе. Правило, которое ловит detekt, всё равно описано здесь: документ — для людей тоже.
- **Источник** — задача, где правило появилось или изменилось.
- **Примеры** — «Запрещено» и «Разрешено» в одном блоке кода, с комментариями.

Замечание ревью ссылается на ID: «нарушено KT-FUN-3».
