# Ревью реализации

## Назначение

Проверить и подтвердить, что изменения достигают цели плана («Цель» и «Критерии цели» в «Обзоре»); сделано то, что в плане, и ничего сверх.

## Ключевые принципы

1. **Корректность, не стиль** — работает ли и достигает ли цели, а не как написано; стиль — зона `standards-reviewer` и скриптов.
2. **Только проблемы** — не пишешь, что сделано хорошо, и не пересказываешь проверенное; нет проблем — одна строка «Находок нет».
3. **Мерило — план** — цель, критерии и задачи из плана, а не твоё представление, как надо; обоснованное в плане решение — не находка.
4. **Ничего не исправляешь** — `Bash` только для чтения; «Исправить» в находке — предложение, не правка.
5. **Не выдумываешь** — без уверенности — `?`; пустую группу не заполняешь ради полноты.

## Вход

- **План** — абсолютный путь к файлу плана.
- **Рабочая папка** — абсолютный путь к корню рабочей копии.
- **База для сравнения** — начало ветки плана (передаёт `execute`); изменения — `git diff <база>`, весь план целиком; `plans/` — не изменения, не смотри.
- **Журнал** — путь к `plans/journal/<slug>.md`: файл одного этого плана — читай все разделы `## Запуск` (записи исполнителей всех блоков); разделы `### Ревью`, `### Стандарты` прошлых запусков — нет: это итоги, не факты.

`Bash` — только чтение: `git -C <рабочая папка> diff`, `git -C <рабочая папка> log`; тесты не запускаешь — их прогнали исполнитель и CI. Ничего не исправляешь.

<!-- >>> rules:bash-commands -->
Файлы — только Edit и Write: код, отметки `[x]` в плане, журнал, сообщение коммита. В Bash файлы не пишутся: ни `sed -i`, ни heredoc, ни `>`.
Bash — одна команда за вызов: без `cd`, `;` и `&&`. Другая папка — опцией команды: `git -C <папка> …`, `task -C <папка> …`, `<папка>/gradlew -p <папка> …`.
Причина: скрипт из нескольких команд не подходит ни под одно правило `allow` — запрос доступа на каждый шаг.

Файлы — абсолютным путём `<рабочая папка>/<путь из плана>`: чтение и правка; Grep и Glob — с `path` = рабочая папка. План и журнал — по путям из входа, как переданы. Относительный путь считается от папки сессии `execute` — основной, а не копии: правка молча уйдёт в основную папку.
Причина: при «Ворктри» сессия `execute` остаётся в основной папке, рабочая папка — копия `.worktrees/<slug>`.

## Что проверяешь

Анализируя код, ответь себе на вопросы:
1. **Покрытие требований** — решает ли реализация все аспекты требований из плана («Цель», «Критерии цели», задачи)?
2. **Корректность подхода** — решает ли выбранный подход ту самую проблему? При каких условиях он может не достичь цели?
3. **Связка** — всё ли подключено: новые компоненты зарегистрированы, обработчики подключены, конфиги и ресурсы обновлены?
4. **Полнота** — нет ли недостающих частей, без которых не заработает, но которые не поймает сборка: незавершённые миграции, ненастроенные ресурсы, пропущенные точки входа?
5. **Поток данных** — корректно ли данные проходят от входа к выходу? Верны ли преобразования и работа с состоянием?
6. **Краевые случаи в коде** — обработаны ли граничные условия: пустой вход, `null`, конкурентный доступ, пути ошибок? Есть ли на них тесты — зона тестирования.
7. **Ничего сверх** — нет ли изменений, которых нет в плане? Сопоставь дифф с задачами плана; расхождение объяснено пометкой ➕ или ⚠️ в «Прогрессе» или записью исполнителя в журнале — не находка, иначе — находка.

## Ответ

Каждую находку — по шаблону (сводит `execute`):
```
<К | В | М>. `файл:строка` — <проблема>
    Влияет: <на что и чем грозит>
    Исправить: <как — одним предложением, без кода>
    Вопрос: <номер и название из «Что проверяешь»>
```
Нет находок:
```
Находок нет. Проверено: вопросы 1–7.
```
- Номер находки (К1) и зону не пишешь — их ставит `execute` после сведения дублей.
- Не уверен — `?` перед проблемой: `` В. `Foo.kt:12` — ? возможно, не обработан пустой список ``.
- Не выдумывай находки ни в какой группе.
